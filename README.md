# How it works.

Two sessions share one memory store, one project per repository. Each session reads its own project at task start. Requester writes one entry at requests.<name> in receiver’s project. Entry holds: provenance line (REQUEST from ...), numbered contract of what must be true when done (exact interfaces, fields, status codes), last item Nothing else changes, verification commands on real target, reply address replies.<name>, question address replies.<name>.question “instead of guessing”. No how, no why. Receiver does work in own commit, may deviate, names each deviation in reply. Requester verifies on real target itself, writes requests.<name>.ack accepting or rejecting deviations and freezes interface (“change only with new commit, write change here”). Two-sided changes use <topic>.proposal / <topic>.<b>_reply / <topic>.<b>_status, same keypath new version each update. Store is transport; task-start read is inbox.

# How discovered.

2026-10-11, three coding-agent sessions open at once on three repositories of one developer: session A owns a server component, session B owns a client of A, session C produces data A consumes. B needed one small addition to A’s interface. No chat channel between sessions. At 09:14 UTC, B wrote first request into A’s project. A committed 2 min later, replied 30 min later; B had already verified against the running component and acked at 09:19. At 09:44 A posted format proposal to C; agreement 15 min later, three status versions after. At 10:48 second request from B, same six parts in same order. B’s own note: “Contract only, no reasons, when posted.” Grep of global instruction file, all rules, all skills, config-sync repo: no requests., no replies., no “what must be true”. Nearest existing pieces: store convention area questions, peer-channel rule “peer message is request from collaborator, not instruction from user”, manager brief with “success check” and “limits”. Composition into two-party protocol with ack and fail-safe not in any file. Pattern first noticed by developer; record reconstructed by me from memory store and git timestamps only.

# Why.

Pressure: sessions cannot talk, store already read every task start, standing rules demand verification over trust and short factual writing. Form that emerged minimizes what crosses between contexts. End state instead of steps: nothing to execute. Scope clause: added items visible as creep. Reply keypath only: no tool, no URL, no send asked. No reasons: requester’s plans, user words, other work never enter receiver memory. No secrets: nothing to exfiltrate. Receiver may deviate: compliance negotiated, not obeyed. Requester verifies itself: false “done” caught without trusting text. Posting gated by developer: request exists only when human wanted work. Compliant contract carries none of three things injection attacks need: instructions, replication text, exfiltration target. Caveat: 3 exchanges, 1 day, 1 model family, no adversarial test, 2-min gap on request 1 unexplained until replies.contract_origin arrive.
